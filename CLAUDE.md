## Project

Astro 331 Lab 8 — **3DOF Reaction Wheel Control** on the small air bearing table (team: Gowri Ramaprasad, Derek Weissinger, Owen Crawley). Full brief: `Astro 331 Lab 8 Overview and Requirements.pptx`.

Goals:
- Reaction wheel attitude control in 3 DOF (pitch, yaw, roll).
- Sensor fusion of gyroscopes, magnetometers, and accelerometers to determine attitude in any state.

Requirements:
1. Hold a specified heading with no visible jitter or drift.
2. Determine true attitude to ±1° in all 3 axes.
3. Automatically detect a simulated or real wheel failure and compensate while still meeting 1 and 2.
- Stretch: slew through a series of 4 attitudes along the optimal path, reaching each within ±1° in all 3 axes.

**Status:** Attitude determination is implemented (build-verified, not yet run on hardware). Everything lives in the PlatformIO project folder:

- `include/quat_math.h` — header-only quaternion + fixed-size `Mat<R,C>` helpers.
- `src/attitude_ekf.cpp` — multiplicative EKF (6-state error: attitude + gyro bias). Gyro propagates; accelerometer update (roll/pitch) with magnitude gating; **heading-only magnetometer update** (`updateMagYaw`, the only update that moves the z gyro bias) fed by the magnetometer aid `src/mag_aid.cpp` (2026-10-27 on; see the mag aid report and `MAG TEST` below). The aid only uses the field in known wheel states (all stopped at a learned shaft position, or all spinning in a direction pattern) against references learned in place; new spinning patterns are learned in place, or predicted from a known one when the aid is stale (`kMagPredictNewPatterns` = false: two fixed-table MAG TESTs disagreed on which is better, MAGTEST_0001/0002 reports; each new pattern costs 0.3–1.2° of reference error), so yaw is held to the heading defined at calibration; elsewhere yaw is gyro-only. **Since 2026-10-31 the aid is OFF at boot** (`kMagAidDefaultOn`; the presentation spot's field is distorted, PROGRESS_LOG §2.24): `MAG ON` enables it (MAG TEST needs it), `MAG OFF` gives gyro-only yaw. - **Yaw gyro scale factor** (`kGyroScaleZ` = 1.009, `SET GYRO_SZ`; 2026-10-31): every gyro z sample is multiplied by it (table frame, before calibration, the EKF and the log, so logs from then on carry the scaled value). The BNO085 under-reads yaw rotation by ~0.9%: measured against the hard-iron-corrected magnetometer heading over two free turns in DEMO_0007; without it SLEW YAW ended a few degrees past the marker after 360° of slews (DEMO_0009).
- `src/imu_bno085.cpp` — Adafruit BNO08x wrapper; enables uncalibrated gyro, accelerometer and **uncalibrated magnetometer**, all at 100 Hz. The gyro sample drives EKF predict + the attitude control step, so **collection and control run at 100 Hz**. The magnetometer feeds the data log and the heading aid (`mag_aid.cpp`).
- `src/data_logger.cpp` — data log, **one row per gyro sample (~100 Hz)**. **No SD file at boot:** sending `BEGIN STATIC TEST [rpm]` (XBee or USB; refused while calibrating) also holds **all four wheels at `kStaticTestWheelRpm` = 100 rpm** via Manual mode (optional rpm argument; `0` = motors off; `DISARM`/`KILL` stops the wheels but logging continues), and opens a new `STATIC_0001.CSV`, `STATIC_0002.CSV`, … (first unused name) and logs every row until power is removed (flush every 1 s, so a power cut loses ≤ 1 s; 32 KB RAM buffer rides out SD stalls; `STATUS` reports `sd=<file>,drop=<n>`). Every 50th row (~2 Hz) streams to the XBee from boot in the same format. Columns: `mcutime_ms` (sample time, µs resolution, 64-bit so it doesn't wrap), `gyro_x/y/z_rad_s` (uncalibrated, not bias-corrected), `accel_x/y/z_m_s2`, `mag_x/y/z_uT` (uncalibrated), `motor_a..d_measured_rate_rpm`, `motor_a..d_duty` (commanded; a coasting dead wheel logs 0), then EKF output: `qw,qx,qy,qz`, `roll/pitch/yaw_deg`, `bias_x/y/z_rad_s`, `sig_roll/pitch/yaw_deg`, `accel_status` (0 applied, 1 gated, 2 singular), `state` (C/I/A/M), demo columns, then `gyro_seq` (the BNO085's own 0–255 report counter) and `gyro_seq_missed` (cumulative reports it sent that the Teensy never got); later appended: `test_step`, `mag_mode`, `mag_resid_deg`, `wheel_status`, `err_*`, `fault_phase`, and (2026-10-30) `enc_a..enc_d` raw encoder counts (shaft positions, for the log replay). **IMU sample loss (open issue):** the static test lost ~1/3 of gyro samples and stalled 50–330 ms in ~20 s-spaced clusters (38 gaps > the 100 ms IMU timeout). `STATUS` reports `miss=` (sequence gaps: lost in transfer), `chipgap=` (late with no sequence gap: the BNO085 itself), `maxgap=` (ms), `lat=` (worst INT-to-read delay, ms), `int=` (INT edges), `svc=reads/timed-from-INT`, `ev=` (reports decoded), `rst=`/`en=` (chip resets / report re-enables). **2026-10-20:** most of the loss was the Adafruit library: `getSensorEvent()` keeps only the last report per transfer and the BNO085 packs gyro+accel+mag into one, so gyro reports were overwritten. `imu_bno085.cpp` now uses its own SH2 callback + queue, reads only when INT is low (20 ms fallback poll), timestamps each report from the INT edge + its SH2 delay, hardware-resets the chip via RST before init (no more power cycle after uploads; fixed 300 ms boot wait; the library itself gets no reset pin), and re-enables reports if none arrive for 0.5 s. First check (idle, SD off): `miss=0`, `maxgap=11` ms, `lat` < 0.05 ms. With SD logging on, SD write stalls still blocked `loop()` (5-min static tests: `miss=102, lat=40` ms, then `miss=12, lat=43` after the first fix). Fixes: `main.cpp` overrides the core's weak `yield()` to call `imu.background()` (reads the chip into a 64-deep queue; guarded against re-entry and before `begin()`), the logger skips writes while the card is busy, and the card now runs in **DMA mode** (`SD.sdfs.begin(SdioConfig(DMA_SDIO))`): FIFO mode spins without `yield()` while the card programs flash. - **XBee link (`Serial8`, 9600 baud ≈ 960 B/s):** data rows (~220–270 B at ~2 Hz ≈ 450–530 B/s) plus command replies, which start with `#`, `S,`, `COUNTS` or `PONG` (data rows start with a digit). Serial8's built-in TX buffer is only 40 bytes, so `main.cpp` adds 1 KB with `addMemoryForWrite`. Without that, every line longer than 40 bytes is silently dropped by the non-blocking senders. Raising the XBee row rate needs a higher baud.

The z (yaw) bias can only come from this average (gravity carries no heading), and the EKF now **locks the z bias** (`EkfParams::lockZBias`; bias walk 1e-6 x/y, 1e-7 z; floor 2e-5 rad/s). **Warm-up matters most:** the BNO085 z bias shifts ~0.007 °/s (≈ 25 °/h of yaw) over the first ~5 min after power-on, so a calibration at boot is wrong minutes later. Heading is held at its start value with the full PD; for roll/pitch the reference tilt is set to the measured tilt every step, so those axes are only **damped** and the table settles where gravity balances it — no steady roll/pitch torque, so the wheels stop filling (holding exact level filled wheel B in ~15 s, DEMO_0003_OLD).   - **`SLEW YAW`** (2026-10-31, built + simulated, not yet run on the table): the stretch test as this pendulous table can do it. Same 4 targets, but only their **yaw** is used: yaw follows the slew profile (rotation about the vertical), while the roll/pitch reference is the measured tilt every step (damping only, as DEMO LEVEL), so the table stays at its rest tilt; heading-hold wheel bias on. Graded like SLEW TEST, with roll/pitch errors measured from the rest tilt (2 s low-pass). Why: each degree away from the rest tilt costs ~11 mN·m (CG ~13 mm low), so tilted targets fill the wheels in < 1 s, and SLEW TEST with yaw-only targets at a fixed roll/pitch (−1.2/−0.2) stopped on the wheel limit 13.5 s in on the table (rest tilt shifts ~0.3° with heading).   - **`SLEW TILT`** (2026-11-01, built, simulated, uploaded; NOT run on the table): tilted targets for the stretch requirement on a table balanced near neutral (CG ~0.5–1 mm below the pivot; being raised with mass at the top screw seats). Needs `SET GRAV_K` (N·m/rad = I (2π/swing period)²; also `SET IXX/IYY` ≈ 0.155). Phases: **scan** (one slow 360° turn, peak 0.05 rad/s, ~200 s, roll/pitch free; fits rest tilt = a0 + a1 cos ψ + a2 sin ψ, the wave being a room-fixed torque; the reference rate includes the slow tilt drift so damping doesn't fight it), then per target **unload** (tilt by δ = h_xy/(k·4 s), ≤ 3°, so gravity drains the wheels' x/y momentum), **slew** (eigenaxis, 0.2 rad/s, 0.05 rad/s²), settle, 5 s hold. Targets are roll/pitch **offsets from the scanned rest tilt** + yaw (`SLEW TSET n dr dp yaw`, defaults +2/0/45, 0/−2/135, −1.5/+1.5/−135, 0/0/0; `SLEW LIST`). Gravity feedforward k·(ref − rest) in the controller. Budget check refuses a target needing > 70% of the x/y wheel capacity. Log phases C (scan) / U (unload). `tools/slewsim` (`sim tilt <room mN·m> <trace|-> <L mm> <tilt scale> <GRAV_K factor>`): 1 mm ±2° and 0.5 mm ±3° pass 4/4 with 0–1.5 mN·m room torque and GRAV_K off by ±30%; 2 mm fails even ±1°.
  - **`FAULT TEST`** (requirement 3; `include/wheel_fault.h`, `src/wheel_fault.cpp`; first draft 2026-10-29, build-verified and simulated, NOT run on the table). **Dead-motor detector** (`DeadMotorDetector`, per wheel, Armed only, in `wheelLoop`): effort e = applied duty − speed/160 (≈ current/stall current); every 0.1 s block, mean |e| ≥ `kDeadEffort` 0.2 with less than 25% of the predicted speed gain (`kMotorAccelPerEffort` 800 rad/s² per unit e) = unresponsive; 0.2 s of those = dead → `wheelEnabled` false, `wheelDead` true, the wheel **coasts** via `WheelMotor::coast()` (zero-current duty; EN/ENB are hard-wired, so `stop()` = brake). Allocation already runs on any 3 wheels. Owen's encoder check (driven > 0.2 duty, < 1 rad/s for 0.5 s, or a speed jump) still disables with a brake; both tell the fault test. The mag aid keeps dead wheels in its wheel-state check (they still turn). **`FAULT TEST <A-D> [s]`** (Idle or Armed): after s s of Armed time (default 10) and once that wheel turns ≥ 3 rad/s, `WheelMotor::setSimulatedDead` holds its motor at zero current while the firmware still sees the commanded duty; whatever is Armed carries on. While it runs the null mode idles the wheels at ±100 rpm (`kFaultWheelBiasRadS`). Graded PASS: right wheel detected ≤ 1 s, controller error back within ±1° (1 s) ≤ 10 s, then ±1° for 30 s. Messages `# FAULT TEST: wheel X motor now DEAD`, `# WHEEL FAULT X: dead motor ...`, `# FAULT TEST: back within ...`, `# FAULT TEST PASS|FAIL ...`. `FAULT TEST REAL` = no injection, grades the first real failure from its detection; `FAULT CLEAR` (Idle) undoes it all. Log columns appended: `wheel_status` (. ok, x failed undetected, D dead/coasting, - off), `err_roll/pitch/yaw_deg` (controller angle error, 0 unless Armed), `fault_phase` (- w F h P X); `STATUS` adds `wst=`, `fault=`. **Motor-level sim** (`Reports/Slew_and_Fault_Simulation.html`): 9/9 PASS, detection 0.6–0.8 s, peak error ≤ 1.0°, no false alarms in 4 healthy runs. Needs all 4 wheels (wheel D's encoder lead is intermittent: fix it first).
  - `src/wheel_motor.cpp`, `include/wheel_speed_ctrl.h` — TB9051FTG dual-PWM drive + encoder speed + 100 Hz PI inner loop (attitude step also 100 Hz) with duty cap, slew limit, and a back-EMF current limit (no current sensing: `|duty − speed/free_speed| ≤ I_limit/I_stall`, 2.5 A of a ~5.5 A stall at 12 V). Speed/gain parameters are sized for 12 V packs and the 6.3:1 gearing (free speed ≈ 160 rad/s per unit duty, measured).
  - `src/command_link.cpp` — ASCII commands on XBee `Serial8` (9600 baud) and USB: `ARM`, `DISARM`/`KILL`, `STATUS`, `PING`, `TEST <A-D> <duty>` (Idle only, 1 s open-loop bench spin), `DEMO SPIN`, `DEMO LEVEL`, `SLEW TEST`, `SLEW SET`, `SLEW LIST`, `FAULT TEST`, `FAULT CLEAR`, `COUNTS` (raw encoder counts per wheel since `ZERO`, plus wheel turns at 400 counts/turn; for hand-turn ratio checks), `ZERO` (zero that readout; any state), `SPEED <A-D|ALL> <rpm>` (from Idle/Manual → Manual state `M`: closed-loop speed setpoints that ramp to the target at `kManualAccelRadS2` (speed-loop integrator held while ramping; feedforward `kManualFreeSpeedRadS`; measured speed low-passed by `kManualSpeedLpfTauS`, which USB telemetry shows while in Manual; all Manual-only, Armed unchanged), clamped to ±`kWheelMaxSpeedRadS` (80 rad/s ≈ 764 rpm since 2026-10-31; was 60), overspeed disarms; `DISARM`/`KILL` → Idle). XBee telemetry is the data-log stream (see `data_logger.cpp`); the estimator CSV (quaternion, Euler, bias, σ, wheel speeds, state, then applied duty A–D appended after `state`) goes to USB at 20 Hz.
  - `src/main.cpp` — Calibrating → Idle → Armed (or Idle → Manual via `SPEED`). Auto-disarm on KILL, IMU timeout, |roll/pitch| > 30°, rate > 2 rad/s, wheel overspeed.
  - **Physics limit:** wheels cannot shed momentum, so a constant disturbance torque (e.g. residual imbalance) fills them in ≈ (wheel momentum capacity)/(torque) seconds, after which the table runs away. Capacity depends on the unmeasured wheel inertia and the wheel speed limit (`kWheelMaxSpeedRadS` = 80 rad/s at 12 V, raised from 60 on 2026-10-31: full motor torque up to ~79 rad/s; ~100 is the practical ceiling once wheel D's drag is fixed); balance quality sets the hold time.
  - **Per-wheel sign bring-up** (`kMotorSign`, `kEncoderSign`): use `TEST A 0.3` etc. with the table clamped. Measured speed must be positive for positive duty (else flip `kEncoderSign`), and the physical spin must be right-hand about the wheel axis (else flip `kMotorSign` and `kEncoderSign` together).
- `include/pins.h` — confirmed Teensy pin assignments (IMU, XBee, wheel PWM, encoders); see "Teensy pin assignments" below. EKF noise values in `EkfParams` are placeholders to tune from a stationary log.

## Hardware

- MCU: **Teensy 4.1** (Cortex-M7, 600 MHz, hardware FPU — `float` math is cheap; prefer `float` over `double`)
- IMU: **Adafruit BNO085** 9-DoF over STEMMA QT (I2C); does on-chip fusion and can output quaternions
- Wireless: Digi **XBee 3** radios — SparkFun XBee Explorer Dongle (USB) on the ground-station PC, XBee 3 on `Serial8` on the table
- Actuators: 4 reaction wheels, each a **Pololu 6.3:1 Metal Gearmotor 37D 12 V** (brushed DC, 64 CPR encoder). All four gearboxes are labeled `GB37-6.3`; confirmed 2026-10-15 by hand-turning each wheel 10 turns with `COUNTS` (~400 counts per wheel turn). The past docs and early firmware assumed 10:1 (640 counts/turn), so **wheel speeds recorded before 2026-10-15's fix read 1.6× low** (multiply old rpm logs by 1.6). Measured ~160–167 rad/s wheel speed per unit duty at 12 V.
- Motor drivers: 4× **Pololu TB9051FTG**, two PWM pins each (from past docs; not yet re-verified on the hardware)

### Board-side wiring (confirmed by the team)

- **TB9051FTG (×4):** Teensy orange → PWM1, blue → PWM2. OUT1/OUT2 → motor red/black. EN tied high, ENB tied low (always enabled). Yellow = GND. **The firmware is configured for 12 V motors** from the Epoch 3S packs (see "Power subsystem" below); earlier the drivers were powered from the Teensy's 5 V VIN pin. As of 2026-10-06 the new power wiring has **not yet been powered up**. OCM, DIAG, OCC are not connected (OCC defaults low).
- **Gearmotor encoders (×4):** blue (Vcc) → Teensy 3.3 V (re-confirmed 2026-10-15), green → GND; yellow (A) / white (B) → Teensy pins above. A/B swing 0–3.3 V, so they're safe for the Teensy with no level shifting. 3.3 V is just below Pololu's 3.5 V minimum encoder supply — if counts are missed or noisy, suspect this first.
- **BNO085:** STEMMA QT red → Teensy 3.3 V, black → GND, I2C on 18/19. **INT → pin 20, RST → pin 21** (wired 2026-10-20). INT must be a plain `INPUT`: with the Teensy pull-up enabled it never read low and the chip sent no reports.
- **XBee (table side):** Digi **XBee 3** (non-Pro, ~40 mA TX @ +8 dBm). VCC → Teensy 3.3 V, GND → GND.
- **Teensy 3.3 V rail budget (250 mA max):** XBee 3 (~40 mA TX) + 4 encoders (~40 mA) + BNO085 (tens of mA) ≈ 100–120 mA. Swapping in an XBee 3 **Pro** (~135 mA TX) would leave little margin.

Notes:
- Yellow/white match Pololu's encoder A/B lead colors. Encoder pins aren't all hardware-quadrature (XBAR) capable; use the interrupt-based `Encoder` library (every Teensy 4.1 digital pin has interrupts).

### Power subsystem

Firmware is sized for 12 V motor packs, but as of 2026-10-06 nothing has been powered on the new wiring. Confirm the as-built state against the plan below before relying on it.

Printable bench wiring sheet (overview + every TB9051FTG pin): `power_wiring.html` (repo root; open in a browser).

Batteries:
- **Motors:** the original packs from the past-documentation dissertation — **four packs, each 3× Epoch 18650 (2600 mAh, 8 A max discharge, protected) in series** = 3S: 11.1 V nominal, 12.6 V full, ~9 V empty. One pack per wheel, one per deck corner for mass balance (dissertation Fig 20).
- **Logic:** one **PKCELL ICR18650 10,050 mAh** pack (Adafruit #5035; 3 cells in parallel, 3.7 V nominal, 4.2 V full, 3.0 V protection cutoff, 3 A max, JST-PH lead rated 2 A), near the center under the Teensy.

Two switches: one **motor switch** for all four Epoch packs and one **logic switch** for the PKCELL.

```
Epoch pack A + ──────────── Driver A VIN
Epoch pack B + ──────────── Driver B VIN       (pack + leads stay separate)
Epoch pack C + ──────────── Driver C VIN
Epoch pack D + ──────────── Driver D VIN
Epoch pack A–D − ─ joined ─ MOTOR SWITCH ─ common ground point

PKCELL + ─ LOGIC SWITCH ─ Pololu U3V70F5 5 V boost ─┬─ Teensy VIN
                                                   └─ Driver A–D VCC
PKCELL −, boost GND, driver GNDs, Teensy GND ── common ground point (never tie pack + terminals together)
```

- **Motor switch:** ZF (Cherry) **CR series** rocker — **single-pole**, rated 20 A @ 125 VAC / 16 A @ 250 VAC (no DC rating confirmed; at 12.6 V and a few amps it's well within what an AC switch of that size handles). Because it's single-pole, it switches the **combined negative** of the four motor packs (low-side). Putting it on the + side would tie the four pack + terminals together — don't. Off = pack negatives float, so no motor current flows. Don't connect any motor pack − to ground anywhere except through this switch.
- **Grounding:** bring the motor switch's output, the four driver GNDs, the boost GND and the Teensy GND to one point (star ground), so motor return current doesn't flow through the Teensy's ground wire.
- **Logic switch:** on the PKCELL + lead, ahead of the boost; ≥ 1 A DC is plenty.
- **Power sequence:** logic on first, then motors (so the firmware has driven the PWM pins low before the wheels get power and they don't twitch at boot — `setup()` waits up to 3 s for USB serial before `WheelMotor::begin()` zeroes the PWM pins, so wait a few seconds after logic on before flipping the motor switch); motors off first, then logic.

- **Before connecting any pack:** split each driver's VIN from VCC (the short orange wire ties them today — left tied, 12 V reaches VCC and back-feeds the Teensy VIN), and cut the Teensy's VIN–VUSB trace so the boost doesn't back-feed USB. **The spare Teensy fitted 2026-10-30 still has VIN and VUSB joined** (the cut didn't separate the pads): never have USB and the logic battery on at the same time — see "Uploading" below.
- Teensy 4.1 VIN accepts **3.6–5.5 V** (PJRC). The PKCELL spans 3.0–4.2 V, so it's in spec when charged but drops below 3.6 V for the end of its discharge. The team chose to boost it to a 5 V rail with a **Pololu U3V70F5** (2.9–5 V in, 5 V ±4% out, ~7 A continuous input, reverse-voltage protection, UVLO 2.4 V falling, ENABLE pin = true shutdown). Add ~33 µF electrolytic across its VIN/GND to suppress plug-in LC spikes. The board is marked **0J11050**, which every U3V70x variant (5–15 V fixed and 4.5–20 V adjustable) shares — the team's board measured **5.09 V out from 4.15 V in** (no load), confirming the 5 V version. Logic load ≈ 0.25 A at 5 V ≈ 0.4 A from the pack, well inside the 2 A lead; runtime ≈ a day.
- The logic has its own pack, so motor surges can't brown out the Teensy/IMU/XBee (the dissertation ran its Arduino off a motor pack and listed that as a possible cause of its oscillations).
- Packs discharge unevenly, so the same PWM duty gives different wheel torque per pack — close a wheel-speed loop on the encoders rather than commanding raw PWM.
- Optional battery monitoring needs a divider (Teensy analog max 3.3 V): 33 kΩ / 10 kΩ on a motor pack (12.6 V → ≈ 2.9 V), 10 kΩ / 20 kΩ on the PKCELL (4.2 V → 2.8 V). Pin 41/A17 is free.
- Charging: Epoch holders have no balancing — remove cells and charge individually; before a run each pack ≈ 12.4–12.6 V with cells within ~0.05 V. Charge the PKCELL with a single-cell Li-ion charger at ≤ 3 A.

### Uploading and running (since 2026-10-30: USB and battery never together)

The spare Teensy's **VIN and VUSB pads are still joined**, so USB 5 V and the boost's 5 V rail would be tied together if both were on: current can flow back into the computer or the boost. Until the pads are properly separated (cut, then confirm no continuity between them):

1. **Motor switch off, logic switch off.**
2. **Plug in USB** (it powers the Teensy by itself) and upload: `pio.exe run -t upload`. PlatformIO finds the board; it is **COM7** on Derek's PC (COM numbers differ per PC; older notes say COM3/COM5). Check it boots: the USB serial shows `# SD: card ready …` and `# BNO085 ready …` (or `BNO085 not responding` on the bench with no IMU).
3. **Unplug USB**, then logic on, then motors a few seconds later. The board reboots and runs its 60 s calibration (keep the table still).
4. **Command and monitor over the XBee only:** the ground-station dongle is **COM5** on Derek's PC, 9600 baud (`PING`, `STATUS`, test commands; ~2 Hz data rows). Logs go to the SD card.

Consequences: there is no USB serial link while the table runs on its battery, so `RAW ON` (100 Hz USB stream) and `tools/mag_cal.py` can't be used; use `MAG MAP` (runs on the board, logs to SD) for magnetometer calibration instead. Once the pads are separated, USB can stay connected with logic on again (uploads then need logic on, since USB no longer powers the board).

## Conventions

- Keep the control loop non-blocking: no `delay()` in `loop()`; use `micros()`/`elapsedMicros` timing so the sensor-fusion and control rates are deterministic.
- Keep sensor drivers, attitude estimation, control law, and wheel fault detection in separate modules so each can be tested independently.
- Angles in code are radians unless a name says otherwise (e.g. `yawDeg`); document frame conventions (body vs. reference) where quaternions/rotations are defined.
